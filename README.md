# a1 — Codex 실기시험 경량 준비물

180분 서비스 개발 시험에서 **SDD + TDD로 필수 구현·검증·설명을 완료하고 토큰 낭비를 줄이기 위한** 짧은 지침과 빈 양식입니다. 시험 문제는 프로젝트 루트의 README.md로 제공된다는 조건을 전제로 합니다.

**공개 저장소: [MAKC-KR1/a1](https://github.com/MAKC-KR1/a1)**. 배포 리비전과 공개 확인 기록은 [PUBLICATION.md](PUBLICATION.md)에 남깁니다. 외부 자료로 사용할 때는 상세 가이드의 허용 범위를 확인하고 실제 사용한 커밋을 기록하세요. 활용하는 저장소는 2차 예선 결과 통지 전까지 공개 상태를 유지해야 합니다.

## 기본 개발 방식: SDD + 핵심 업무 TDD

**SDD(Spec-Driven Development)**로 무엇을 만들지 짧게 명세하고, **TDD(Test-Driven Development)**로 핵심 업무 규칙을 실패 테스트 → 최소 구현 → 구조 개선 순서로 개발합니다. 서비스 아키텍처의 기본안은 **한 애플리케이션 안에서 업무 기능을 나누는 모듈형 모놀리스**입니다. 기존 프로젝트의 구조와 시험 요구가 우선입니다.

```text
문제 README + 사용자가 전달한 담당자 답변
  → SPEC: 요구사항 ID·인수 조건·입출력 계약
  → 한 업무의 실패 테스트 실행
  → 통과하는 최소 구현
  → 동작을 유지하며 구조 개선 + 재검증
  → 실제 연결 경로 검증
  → 다음 업무 / 최종 코드 근거 설명
```

명세와 실제 동작을 계속 맞추는 방식입니다. 처음부터 모든 상세 설계를 끝내지 않고, 다음에 구현할 업무의 계약을 정한 뒤 진행합니다. 이미 확정된 조건은 추가 승인 없이 구현하며, 결과를 바꾸는 미확정 사항은 필요할 때마다 사용자에게 질문합니다.

- `.exam/SPEC.md`: 확인된 요구사항과 인수 조건의 단일 정리본. 원문·실제 답변과 충돌하면 확인합니다.
- `.exam/STATE.md`: SPEC의 ID를 참조하는 현재 작업·실제 검증 기록. 명세를 복제하지 않습니다.
- 테스트: 핵심 업무의 정상·경계·오류 동작을 확인합니다. 테스트를 실행해 필요한 기능이 없어 실패하는지 확인한 뒤 구현합니다.
- 코드: 입력 처리 → 업무 규칙 → 저장·외부 연동의 책임을 나눕니다. 필요한 만큼 함수·모듈로 분리합니다.

구체적인 작업 순서·아키텍처 선택 기준은 [WORKFLOW.md](WORKFLOW.md)에 있습니다. 시작 프롬프트에 핵심 규칙이 포함되어 있으므로 매번 문서 전체를 읽힐 필요는 없습니다.

## 프로젝트 디렉토리 구조

현재 시험 프로젝트 안에 `a1/`을 가져옵니다. 경로 입력은 없습니다. 아래는 기존 코드 구조가 없을 때의 기본안이며, 파일·폴더는 필요할 때 만듭니다.

```text
현재 시험 프로젝트/
├── README.md                 # 제공된 문제 원문 보존
├── src/
│   ├── features/             # 업무별 구현
│   │   └── <업무>/           # 입력 처리·업무 규칙·저장 연동
│   └── shared/               # 실제로 여러 업무가 공유할 때만
├── tests/
│   ├── unit/                 # 핵심 업무 규칙
│   └── integration/          # API·저장 등 실제 연결 계약
├── .exam/
│   ├── SPEC.md               # 요구사항·인수 조건·계약
│   ├── STATE.md              # 현재 작업·검증
│   ├── SOURCES.md            # 실제 사용 자료
│   ├── AI_USAGE.md           # 주요 AI 활용 기록
│   ├── EXPLAIN.md            # 최종 설계 설명·질문 답변
│   └── logs/                 # 필요한 상세 로그만
└── a1/                       # 공개 준비물, 서비스 코드 작성 위치 아님
    ├── START_PROMPT.md
    ├── WORKFLOW.md
    ├── prompts/
    └── templates/
```

프레임워크가 `app/`, `pages/`, 테스트 인접 배치 등 다른 관례를 사용하면 그대로 따릅니다. 기존 코드를 이 구조에 맞추려고 옮기지 않습니다. UI가 있는 과제에서는 필요한 화면을 실제 업무 처리 경로에 연결합니다.

## 시험에서 사용하는 순서

문제 `README.md`가 있는 현재 프로젝트 루트에서 실행합니다. 셸 예시는 bash/zsh 기준입니다.

1. 온라인 반입과 Git 사용이 허용되면 준비물을 가져옵니다. 기존 `a1/`이 있으면 내용을 확인해 사용합니다.

   ```sh
   git clone https://github.com/MAKC-KR1/a1.git a1
   ```

   네트워크가 차단돼 있으면 승인된 ZIP 반입 방식으로 `a1/`에 풉니다. `a1/README.md`는 사용법이며 루트 문제 README를 덮어쓰지 않습니다.

2. 빈 작업 양식을 준비합니다. 기존 파일은 보존합니다.

   ```sh
   mkdir -p .exam
   cp -n a1/templates/*.md .exam/
   ```

   파일 반입이 제한되면 허용된 입력·메모 방식으로 필요한 항목만 기록합니다. `.exam/logs/`는 필요할 때 만듭니다.

3. 저장소 URL·실제 커밋·사용 파일·MIT 라이선스를 `.exam/SOURCES.md`에 기록합니다. Git 사용 리비전은 다음 명령으로 확인합니다.

   ```sh
   git -C a1 rev-parse HEAD
   ```

   ZIP은 다운로드한 실제 커밋·URL을 기록하고 확인할 수 없는 값은 미확인으로 남깁니다.

4. 현재 시험 프로젝트에서 제공된 Codex를 사용합니다. [START_PROMPT.md](START_PROMPT.md) 내용을 첫 메시지로 전달합니다. 작업공간 경로 입력이나 추가 Skill 설치는 필요하지 않습니다.
5. AI가 README를 읽고 SPEC을 정리합니다. 담당자 확인이 필요하면 사용자에게 질문합니다. 사용자가 답변을 전달하면 SPEC에 반영하고, 확정된 업무부터 TDD로 구현·검증합니다.
6. 제출 전 SPEC의 필수 항목을 코드·테스트와 대조하고 EXPLAIN을 한 번 작성합니다. 시험 제출 경로와 지침에 따라 코드·기록을 제출합니다. 별도 Git 저장소인 `a1/`을 서비스 코드와 함께 일괄 추가하지 않습니다.

문제 원문과 기존 프로젝트 지침을 보존하고 제공된 Codex 버전을 유지합니다. 설치·업데이트, Python, 외부 API 키, 별도 모델 실행기는 필요하지 않습니다. 이 저장소는 일반 지침과 빈 양식만 제공합니다.

## 담당자 확인이 필요할 때

원문과 확인된 답변으로 결정할 수 없는 사항은 **질문 수·횟수 제한 없이 필요할 때 사용자에게 질문**합니다. 사용자가 담당자와 대화하고 실제 답변을 AI에게 전달합니다. AI가 담당자 답변을 만들어 내거나 추측으로 확정하지 않습니다. 답변이 필요한 모호한 작업은 보류하고, 기다리는 동안 확정된 독립 작업을 계속합니다. 확정된 답변은 SPEC에 반영하고, 그에 따른 작업 변경만 STATE에 짧게 남깁니다.

## 토큰을 줄이는 운영 규칙

| 반복 비용 | 적용할 방법 |
|---|---|
| 여러 에이전트에 같은 명세·대화 복제 | 주 에이전트 1개가 기본. 독립 작업에만 보조 1개를 필요시 사용 |
| 매번 전체 저장소 읽기 | 시작에 문제·실행 설정 파악, 이후 파일 검색과 관련 구간만 읽기 |
| 장문 계획·보고·코드 재출력 | 한 작업씩 지시, 일상 보고는 변경 파일·검증·다음 조치 5줄 내, 필요한 질문은 별도 |
| 여러 문서를 매 작업마다 재생성 | 명세는 SPEC, 실행 상태는 STATE에 한 번만 기록하고 변경된 항목만 갱신 |
| 같은 오류에 무작정 재시도 | 재현 입력·실제 로그·관련 코드로 원인을 좁히기 |
| 상시 리뷰·설명 에이전트 | 필요할 때 범위를 좁혀 검토하고, 최종 설명은 한 번 작성 |

한 작업은 하나의 완료 조건으로 묶습니다. 작은 수정마다 새 에이전트를 만들거나, 전체 기능을 한 번에 모호하게 요청하지 않습니다. 모델 응답이 실제 파일로 저장되면 같은 코드 전체를 채팅으로 다시 받지 않습니다.

검증은 변경에 영향을 받는 검사부터 실행하고, 제출 전 필요한 통합·핵심 시나리오 검증을 수행합니다. 토큰 절약을 위해 테스트를 생략하거나 실패 검사를 약화하지 않습니다. 짧은 프롬프트와 파일 읽기 범위는 운영 방침이며 제공된 Codex의 내부 컨텍스트 처리·캐시·과금량을 강제로 제어하는 기능은 아닙니다.

## 권장 모델과 사용 기록

시험 안내의 권장 표시명은 **6.1 Sol, 5.6 Terra, 6.0 Luna**입니다. 이름을 다른 모델 버전으로 바꾸지 않습니다. 이 안내만으로 모델별 토큰 효율·성능 순위를 판단할 수 없으므로 특정 모델이 더 적은 토큰을 쓴다고 단정하지 않습니다.

시험 환경에서 제공되는 권장 모델 중 검증된 한 모델로 시작하고, 동일 작업을 여러 모델에 반복해서 맡기지 않습니다. 전환은 구체적인 실패 원인이나 작업상 필요가 있을 때만 합니다. 모델 선택권·하위 에이전트 기능이 없다면 제공된 한 모델로 역할을 순서대로 수행합니다.

[AI_USAGE.md](templates/AI_USAGE.md)에 중요한 작업별 목적·모델·사람의 확인·실제 검증을 짧게 기록합니다. 토큰 사용량을 화면이나 로그가 제공하지 않으면 미제공으로 남깁니다. 숨겨진 사용량에 대한 정확한 최소값이나 절감률을 보장하지 않습니다.

## 시간과 설명

20분 요구사항 확인, 35분 실행 환경·계약, 80분 핵심 흐름, 125분 기능 추가 중단, 160분 제출 준비, 180분 제출 완료를 기준으로 삼습니다. 시간은 시험 타이머를 사용하고 필요할 때 남은 시간을 AI에 알려줍니다.

[EXPLAIN.md](templates/EXPLAIN.md)는 제출 직전에 실제 코드·검증 기록으로 채웁니다. 작업 중에는 SPEC에 설계 선택과 근거를 짧게 남겨 최종 정리 때 전체 분석을 반복하지 않도록 합니다.

## 출처와 공개 상태

사용 자료는 [SOURCES.md](templates/SOURCES.md)에 URL·커밋·사용 파일·라이선스·직접 수정한 부분을 기록합니다. 공개 자료 활용 허용은 상세 가이드의 범위 안에서 적용됩니다. 공개라는 이유만으로 어떤 자료·반입 방식이든 허용된다고 가정하지 않습니다. 외부 결과물로 과제를 통째로 대체하지 않습니다.

공개 저장소에는 이 일반 지침·빈 양식만 게시합니다. 실제 시험 README, 담당자 대화, 해답, 제출물, 실행 기록은 포함하지 않습니다. 게시 준비 사항은 [PUBLICATION.md](PUBLICATION.md)에 정리했습니다.

Codex에서 AGENTS.md가 인식되며 다른 기록 파일은 선택적 운영 관례라는 점은 [OpenAI 공식 워크플로 문서](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)를 참고했습니다. 이 경량 패키지는 기존 AGENTS.md를 수정하거나 별도 파일의 자동 로딩을 전제하지 않습니다. 시험 안내와 제공된 버전에서 실제 지원되는 동작을 우선합니다.
